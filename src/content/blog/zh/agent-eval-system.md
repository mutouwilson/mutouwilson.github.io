模型的评估通常从一道题和一个标准答案开始。Agent 不太一样。它要在环境中工作：理解一个不完整的请求，规划路径，调用工具，在变化的数据源里做判断，再交付一个可以被人接手的结果。对于线上产品，要回答的一个终极问题是，有没有真正的帮助到用户完成工作？

因此，Agent 评估的目标不应该只是给模型排名，而是建立一套产品语言：当我们说"这个版本更好"，大家知道它在哪类任务上变好了、依据是什么、又是否在真实的业务使用中成立。

> 一套 Agent 评估系统，至少要把任务集、判定方法、比较方式和线上反馈连成一个闭环。

## 一、评估系统先从产品任务开始

现在有很多评估项目一开始就讨论 metric 或 judge。其实更应该先做的是把产品任务拆出来。因为不同任务的真值是不同的：有些任务存在明确答案，有些只能由领域专家判断，有些要等到用户行为发生后才能知道好坏。

从具体的业务场景出发。先看招聘工作流：从需求澄清、人才研究与搜寻，到初步筛选、触达推进，再到面试、选择和录用。这是产品要服务的业务地图。对应的就是评估任务了，按照真值和交付形态的维度，我们可以把 Agent 能被独立评估的工作单元拆开。

**招聘工作流**：需求澄清 → 人才研究与搜寻 → 初步筛选 → 触达与推进 → 选择与录用。说明产品覆盖了哪段业务。

**评估任务类型**：Known-item Lookup、开放式 Sourcing、Talent Mapping、闭池 Screening、Outreach。决定 case 的真值、判定配置与测量方式。

具体看招聘 Agent 的评估任务类型。虽然表面上都与"找人"有关，但评估配置完全不同。

| 评估任务类型 | 对应的业务环节 | 可依赖的真值 | 例子 |
| --- | --- | --- | --- |
| **Known-item Lookup** | 人才研究与搜寻 | 目标 profile、别名、渠道 ID | 找到某公司现在的 CTO。 |
| **Open Sourcing** | 人才搜寻与初步筛选 | 硬条件、候选人证据、招聘专家判断 | 为 AI Infra 负责人职位找一组可聊的人。 |
| **Talent Mapping** | 人才研究与搜寻 | 组织边界、人员名单、覆盖池 | 整理某赛道公司的研究负责人和技术骨干。 |
| **Closed-pool Screening** | 初步筛选 | 简历、明确的纳入与排除条件 | 从 500 份简历中筛出符合地点与技能门槛的人。 |
| **Outreach & Engagement** | 触达与推进 | 收件人、触达规则、候选人回复与后续事件 | 为 shortlist 写个性化首封信，控制重复触达并跟进回复。 |

任务类型只是数据集的第一层。第二层是细化的业务场景：行业、职能、职级、地域和候选池规模。高管职位的可选池可能不到一百人，更像一个可枚举的 mapping 问题；高频中端岗位则要在大候选池里考验搜索和筛选。第三层就是我们 Agent 的能力标签了，例如多跳检索、多源验证、跨域检索和大海捞针。

因此，我们构造一条 case 的时候最好不是一段简单的 prompt，而是一个坐标：`任务类型 × 业务场景 × 能力标签`。数据集由这些坐标构成，这样题集扩展时，我们能看见漏掉了哪些真实场景；分数变化时，也知道变化发生在什么地方。

## 二、每一类任务，都要有自己的判定配置

数据集回答"评什么"。判定配置回答"这一类任务怎么判"。我们需要把预期结果、可接受的证据和判定器写清楚。当前公开的 Agent 基准也正在向这个方向收敛：证据充分时用确定性检查；只有语义无法穷尽时，才使用模型判断。[Agents' Last Exam](https://arxiv.org/abs/2606.05405)、[Claw-Eval-Live](https://arxiv.org/abs/2604.28139) 和 Anthropic 的 agent eval 工程指南都采用了类似分工。

| 判定层 | 判定什么 | 说明 |
| --- | --- | --- |
| **L0 断言** | 预期对象或状态是否出现。 | 适用于 known-item lookup、可枚举的人才地图。目标 profile 在 top-k，便是通过；没有找到，便是失败。长任务可以拆成 vital / okay 子项，重复运行看 `pass^k`。 |
| **L1 约束** | 不可妥协的业务条件与过程约束是否被满足。 | 地点、任职状态、工作年限、来源证据、渠道合规、重复触达，都应该由事实和规则来判断。严重违规应当直接拦截，而不是在总分里扣一点。 |
| **L2 语义** | 在满足硬条件之后，这份交付是否更合适。 | 开放式 sourcing 常常需要这一层：逐项判断经历、技术深度和迁移性，要求引用证据，并通过人工金标校准模型 judge。 |
| **L3 结果** | 交付有没有在真实工作流中产生效果。 | 保存、接受、联系、回复、面试，属于对部分线上交付的长期观察。检验离线结论是否与用户价值相关。 |

这四层是系统拥有的四种判定能力，不是每条 case 的必经路径。一个 known-item lookup 可以只有 L0；封闭池 screening 主要是 L1；开放式 sourcing 常常需要 L1 和 L2；L3 则在上线之后才出现。关键是：每条 case 都要明确自己使用哪些层，以及为什么。

| 任务类型 | L0 断言 | L1 约束 | L2 语义 | L3 结果 | 说明 |
| --- | --- | --- | --- | --- | --- |
| Lookup | ● | ○ | ○ | ○ | 目标是否命中 |
| Screening | ○ | ● | ○ | ○ | 规则是否执行 |
| Sourcing | ○ | ● | ● | ○ | 结果是否合适 |
| Mapping | ● | ● | ○ | ○ | 覆盖是否足够 |
| Outreach | ○ | ● | ○ | ● | 触达是否有效 |

*● 启用该层，○ 非必须，判定层是可组合的能力，而不是所有 case 都必须经过的流水线。*

## 三、设计能力探针，评估 Agent 的核心能力

对招聘 Agent，我们在实现的过程中不仅仅只靠"推理能力"，还会依赖于另外几种能力：跨源取证、多跳检索，以及跨越封闭域（closed domain）与开放域（open domain）的混合检索。这些都需要刻意的构造；如果只是从生产请求里随机抽样，题集最后很容易被单渠道、短路径、单域的简单任务填满。

| 能力探针 | 题目真正难在哪里 | 怎样构造 | 优先判定 |
| --- | --- | --- | --- |
| **多跳推理检索** | 必须串起多个分散事实，才能锁定目标候选人；不是在一个 profile 上逐项勾条件。 | 先选定真实目标候选人，枚举其跨来源属性，再反向写出查询。目标候选人保持可验证，难度由跳数和每一跳的冷僻度控制。 | L0：目标是否找到。必要时补 L1：关键证据是否覆盖。 |
| **跨源聚合** | 任何单一渠道都不足以完成判断：候选人可能在 A 源，决定性经历或联系方式在 B 源。 | 构造"单源解不出"的 case；要求最终证据来自相互独立的来源，而不是把同一条信息的转载算作多源。 | L0：关键对象是否覆盖；L1：证据是否跨源、可追溯。 |
| **跨域 / 混合域检索** | 封闭域要求不漏：候选池给定、可枚举，查全可以算清楚。开放域没有边界：覆盖未知，全靠检索策略。混合域两边都要做对，还要把两边找到的同一个人对上。 | 同一个 JD 构造两种配置：只允许封闭池作答，或在封闭池里只埋部分答案、其余必须去开放域补齐。 | 封闭域可枚举，用 L0 / L1 算查全；开放域与混合域用 L2。 |
| **招聘版"大海捞针"** | 在足够大的候选池中，只有少数人同时满足全部条件，干扰项又高度相似。 | 冻结可回放的候选池，埋入唯一满足条件的目标候选人；用池规模和干扰项相似度调节难度。 | L0：目标是否被找回；L1：筛选条件是否完整执行。 |

能力探针最重要的是要做到**难解易验**：Agent 必须使用目标能力才能解题，最终的结果要可以明确的复核。
其中多跳题很容易被误写成多约束题，如果所有条件都能在同一个 profile 上逐项验证，它其实评估的是 L1 条件筛选，不是跨实体、跨来源的信息链。

另外还要注意的一点是，要防止模型自身知识的干扰。我们用的 LLM 本身已经学到了海量的世界知识，所以设计的目标候选人不应是模型可以直接背出的高知名度对象；多跳题至少保留一跳来自较新的证据，并与训练、缓存和内部候选库隔离。
当通过率接近饱和时，也不必急着换一套指标，可以增加一跳、扩大来源分散度，或者提高干扰项相似度。这使探针既能主动压测能力，也能随 Agent 的进步继续工作。

## 四、绝对与相对两种测量模式

同一套判定配置，需要在两种模式下运行。绝对评估回答"有没有达到预期"；相对评估回答"是否比基线更好"。各有应用场景，如果把这两件事混在一个分数里，就很难清晰的解释结果。

**绝对评估**：目标候选人是否找到；硬条件是否满足；交付是否有足够证据；一次发布有没有破坏既有能力。适合做回归门禁。

**相对评估**：两个检索策略谁带回更多可用候选人；两套执行过程谁更贴合 JD；新版本是否优于基线。适合做方案选择。

开放式 sourcing 的难处在于，没人知道世界上所有合适候选人。因此没法去评估"recall"。能采用的办法是把多个系统的候选结果并池、补充人工判断，计算相对池覆盖率。

## 五、落地中的一些关键点

任务集、判定配置和测量模式定义了系统的骨架。要让它真的可用，还要处理三个工程问题：判定器是否可信、运行环境是否可比，以及线上的反馈如何接回离线系统。

1. **校准判定器**：L2 的 judge 是一种判定器。既要有好的 case、也要有坏的与边界情况的 case 做人工金标集，定期比较 judge 与专家的一致性。
2. **锁定运行环境**：记录数据集、模型、harness、工具快照与判定器版本。能回放的环境负责做回归；生产流量负责观察真实线上情况的变化。
3. **接回业务结果**：关联产品版本、任务类型与线上行为，回流用户接受、联系、反馈等标签。未反馈的不一定是负例，同时太低频的录用结果也不适合拿来指导日常调参。

没有人工校准，L2 的标准会漂；没有环境与版本记录，历史分数无法比较；没有线上回流，离线评估就不知道是否真的代表用户价值。任何一个部分缺失，另一个部分都很难独立成立。

## 六、评估系统是长出来的

实施的时候，第一版数据集不需要很大，最可靠的来源，可以采用生产中的 bad case，比如漏掉关键人，错配，该停却没停，空结果交付。这些 case 本身就是评估系统最有价值的增量。
处理流程大致如下：

1. **线上反馈**：保存请求、交付、trace、环境与版本。
2. **任务归类**：确认它属于哪类任务和业务场景。
3. **配置判定**：可断言进 L0，硬条件进 L1，语义争议进 L2。
4. **加入回归集**：修复后重跑，并继续观察线上结果。

好的 benchmark 不是一次性写出来的，而是随着产品理解和真实失败逐步沉淀。

最后，Agent 评估系统产出的不只是一个总分，最重要的是一种持续的判断能力：我们知道在什么任务上变好了，为什么相信这个结论，也知道下一步该改产品的哪里。
