Agent 产品的质量，不能止步于"交出一份结果"。它最终要被用户采用，并在真实工作里产生效果。

---

## 一、怎么定义一个 Agent 的"好"

面向用户的产品，最后总会落回"多、快、好、省"四个字。覆盖是否足够多，响应是否足够快，结果是否足够好，价格是否合理。Agent 产品当然也不例外。

对于 startup 阶段的 agent 产品来说，"好"往往比"多、快、省"更为重要。用户愿意把招聘、销售、研究这样的实际工作交给一个新工具，并持续使用它，并不是因为它"能用"，而是因为它确实在某个环节更加好用（往往需要 10 倍体验）。

在讨论 Agent 质量时应该首先避开一个误区：把"agent 跑完了"当作"用户拿到了好结果"。过去两年，agent 在工具调用、浏览器操作和长任务编排上的进步很快。相比早期会原地打转的 demo，现在不少系统已经能够稳定地跑完一条任务，也能交付一份看上去完整的结果。

但在招聘场景里，这只是第一步而已。比如：我们的 Agent 确实给出了二十位候选人，但并不等于这二十位真的匹配；候选人匹配，也不等于 recruiter 会推进；recruiter 推进，更不等于产生回复或面试。所以真正难的，是把这条链一层层走完，拿到真正的业务结果。

## 二、招聘 Agent 的"好"，是一条五层结果链

以一次 sourcing request 为例，招聘 Agent 的端到端质量可以拆成五层。它们是从系统结果走向业务结果的一条链：每往上一层，离用户价值更近，定义和测量也更困难。

| 层级 | 名称 | 含义 |
| --- | --- | --- |
| L0 | 稳定运行 | 任务能进入预期终态，不 crash、不超时、不空转。 |
| L1 | 任务完成 | 形成 recruiter 可以承接的交付，而不只是模型说"done"。 |
| L2 | 交付正确 | 候选人、匹配判断、证据和联系方式经得起核验。 |
| L3 | 用户采纳 | 结果被保存、接受、联系，真正进入招聘工作流。 |
| L4 | 业务达成 | 在约定窗口内带来回复、面试、offer 等业务结果。 |

*图注：从"能跑"到"有业务效果"，每一层都会筛掉一部分任务。*

端到端地看主指标。

| 层级 / 主指标 | 端到端计算口径 | 招聘业务里的含义 |
| --- | --- | --- |
| L0 稳定运行率 | 稳定进入预期终态的任务 ÷ 可评估总任务数 | 浏览器、数据源、模型或工作流没有让任务中断或空转。 |
| L1 任务完成率 | 满足交付契约的任务 ÷ 可评估总任务数 | 至少交出候选人、匹配理由、证据、联系方式状态和限制说明。 |
| L2 交付正确率 | 通过质量 rubric 的任务 ÷ 可评估总任务数 | hard requirement 命中；每个关键判断有可追溯证据；未知项没有被编造。 |
| L3 用户采纳率 | 至少一位候选人被保存、接受或联系的任务 ÷ 可评估总任务数 | recruiter 认为这份交付值得放进自己的 pipeline。 |
| L4 业务达成率 | 在归因窗口内发生预设业务事件的任务 ÷ 可评估总任务数 | 例如产生有效回复、进入面试；不同职位要事先约定口径与观察窗口。 |

"可评估"也要有边界。启动前被用户取消、输入不合法、或产品在执行前已明确拒绝的请求，应单列为 `excluded`，而不是混进分母后再解释掉。

## 三、要提升五层指标，需要从 Agent 执行过程中分析

分析怎么提升指标值，还是得回到一条任务的执行过程。大多数 agent 的内部形态不同，但摊开来看，通常都绕不过五个环节：理解、plan、执行、验证、停止。

| # | 环节 | 做什么 |
| --- | --- | --- |
| 01 | 理解 | 把 JD 变成可执行的条件；识别需要问用户的歧义。 |
| 02 | Plan | 根据数据源、时间和工具约束，安排搜索、筛选和补证路径。 |
| 03 | 执行 | 调用数据源和工具，处理失败，拿到候选人与原始证据。 |
| 04 | 验证 | 核对 hard requirement 与证据；把不能确认的内容留为未知。 |
| 05 | 停止 | 判断何时已满足契约，何时该换路、求助，或诚实地部分交付。 |

*图注：过程环节用于归因；五层结果用于衡量交付。*

| 环节 | 诊断指标 | 主要影响的结果层 | 典型问题 |
| --- | --- | --- | --- |
| 理解 | 需求理解准确率、criteria 抽取完整率、该问不问率。 | L1 任务完成率、L2 交付正确率 | 把 must-have 当 nice-to-have；遗漏地区、职级或行业限制。 |
| Plan | 关键路径覆盖率、资源约束覆盖率、replan 合理性。 | L0 稳定运行率、L1 任务完成率 | 没有考虑浏览器权限或数据源限制；候选人不够时没有补充路径。 |
| 执行 | 工具选择正确率、参数正确率、动作成功率、重复动作率。 | L1 任务完成率、L2 交付正确率 | 分页重复、DOM selector 漂移、来源选错、联系方式补全失败。 |
| 验证 | 验证器查准率、查全率、证据覆盖率、与人工判断的一致性。 | L2 交付正确率、L3 用户采纳率 | 候选人看似符合 criteria，但证据不足；judge 放过了无来源推断。 |
| 停止 | 早停率、过度执行率、空转率、soft cap 收尾质量。 | L1 任务完成率；也影响成本与时延 | 名单没找够就 commit；已经满足 shortlist 还继续调用工具。 |

在这里最容易犯的错误，是把过程指标当作质量本身。比如 plan 写得很完整，不代表候选人是对的；工具调用全部成功，也不代表联系方式真实可用。过程指标只负责解释：L2 为什么掉了，L1 为什么没形成，L0 为什么没有跑稳。所有优化都应先从端到端结果出发，再沿着 trace 往回找。

## 四、构建一个可落地的系统

### 1. 先写任务契约

每条 sourcing request 在开始时就应该有结构化的职位、地区、职级、must-have、排除条件、期望候选数、数据源边界和目标事件。任务完成不是由模型自己说了算，而是由这份契约决定。市场上人选不足时，交付"结果不足，但已完成了哪些搜索和验证"也可以是好的完成；反而假装找到了足够人选，不是。

### 2. 保留可以回放的执行记录

每一步的工具调用、输入、返回、错误、重试、验证结论和停止原因都要进入 trace。从日志中我们可以分析出：这一批任务为什么 L0 降了？是浏览器 gate、数据源限流，还是同一动作在重复？一条 L2 失败的候选人，是检索源错了，还是判据校验漏了？

### 3. 把交付变成可检验的结构

候选人、每条匹配判断、对应证据、联系方式、未知项、限制说明，都应该尽量结构化。这样 L1 可以自动检查交付是否完整；L2 才能按 rubric 抽检，而不是让 reviewer 在一段自然语言里猜模型做过什么。

### 4. 用人工校准正确率，不把 judge 当真相

LLM judge 适合扩大覆盖面，但不能单独定义正确。我们应该每周从不同职位、地区和失败类型中分层抽样，由人工对 hard requirement、证据正确性和未知项诚实性做标注，再用这批标注去校准自动化 rubric。外部 agent benchmark 已经从静态答案走向环境中的任务结果；我们的优势在于，招聘业务自己就拥有更贴近真实价值的 criteria、候选数据和 recruiter review。[AgentBench](https://arxiv.org/abs/2308.03688)、[OSWorld](https://arxiv.org/abs/2404.07972)、[τ-bench](https://arxiv.org/abs/2406.12045)

### 5. 接上用户与业务回流

对于 L3 和 L4，它们的信号不会自动出现在 trace 里。我们的产品上需要记录 recruiter 是否保存、接受、联系，以及拒绝的原因；再从 ATS 或 outreach 流程回流回复、约面等事件。最后 L4 的噪声是最大的，适合按职位 cohort 做月度观察，然后和人工 sourcing 或历史基线比较，而不是拿某一周的波动指导 prompt 调整。

> 先拿已有 trace 算 L0 和 L1；再建立小规模 golden set 和人工抽检，得到可信的 L2；随后补齐 accepted、contacted、reject reason，开始观测 L3；最后才用 cohort 接 L4。
>
> 这样做的好处是，每多一层数据，前一层都已经有可解释的基础，逐步叠加、逐步深入。

## 结语

对 Agent 来说，"好"不该是一个笼统的满意度，也不是某一次模型回答得多漂亮。它是一条从稳定运行到实际业务效果的五层结果链。把这条链拆开，我们既能看到最终价值有没有发生，也能知道应该回到理解、计划、执行、验证还是停止去解决问题。

能跑完，是 agent 的起点；交出正确且被用户采用的结果，才是它开始成为生产级产品的时刻。
